## 第一部分 · 整条技术路径

### 1. 一句话说清这条路

> **把「记忆」从上下文窗口搬到参数里：主干冻结，旁路挂一组可单独写入、可单独擦除的低秩记忆槽；
> 写入靠运行期梯度，读取靠前向传播（不占上下文），遗忘靠精确擦除 + 效用/时间淘汰。**

### 2. 信息是怎么流动的

```
        一段对话
           │
           │ ① 写入判据：这条值不值得刻成钢印？（惊讶度 / 显式指令 / 信息增益）
           ▼
   ┌───────────────────────────────┐
   │ ② Write：k 步梯度，只更新一个秩块 │   目标项：只开本槽（学"查询→答案"）
   │    + 锚定项：惩罚对基座的改动      │   锚定项：开已写槽（惩罚槽间串扰）
   └───────────────┬───────────────┘
                   ▼
   ┌───────────────────────────────┐
   │ ③ 存：槽位 = 秩维度上的一段       │   K 个槽 × 每槽 rank r；容量 = K
   │    元数据 = 效用 / 时间 / 是否钢印 │   持久化到磁盘 ⇒ 跨会话
   └───────┬───────────────┬───────┘
           │               │
   ④ 遗忘  ▼               ▼ ⑤ 读取
   效用/时间衰减           查询 → 前向 → 答案
   淘汰 → **精确擦除**     （记忆内容**不进上下文**）
   （擦除后位级回到初始态）
```

### 3. 三个设计决定，以及为什么

| 决定 | 选择 | 为什么不选另一条 |
| --- | --- | --- |
| **记忆载体** | rank-blocked LoRA（单个适配器内部按秩切块） | 不选"另加一整层网络"：8 GB 显存下新层要与冻结主干对齐、训练不稳，且**无法单独擦除某一条**；也不选"多个独立适配器"（ProCL 的做法）：显存与推理开销随条数线性增长 |
| **遗忘方式** | **精确擦除**（把该秩块恢复成初始态） | 不选"权重衰减到很小"：衰减不可验证，永远无法断言"这条真的没了"；选精确擦除的代价是容量变成离散的 K |
| **读取方式** | 前向隐式生效，**不需要检索步骤** | ⚠️ **这条正在被实测挑战**：见下面第五部分的瓶颈 |

### T1 · 最小闭环：写得进、擦得净　【基本完成，读时组合未解】

| 项 | 内容 |

**【实测】T1 已核验的数字**（2026-09-29）：

| 断言 | 读数 | 含义 |
| --- | --- | --- |
| 只开本条自己的槽去读 | **4/4** | 写进去了，也读得出来 |
| 只开别的槽去读（P4 的 SHUFFLE） | **0/4** | 槽是查询专一的，没有串读 |
| 开全部槽去读 | **1/4** | 🔴 **瓶颈：读时叠加** |
| 擦除后 vs 从未写过 | **逐字符相同 5/5** | 精确遗忘成立 |
| 写入隔离断言 | **全部 True** | 写入不污染别的槽 |
| 单条写入耗时 | **32–57 s** | 太慢，主因是锚定项要对 6 个 prompt × 15 万词表算 KL |
| 锚定项效果 | 旧表述为 `anchor KL = 5.68 ⇒ 失效`，**已订正** | 🔴 **锚定项确实在空转，但原因是结构性的**：它当时按"全部已写槽求和"求 KL，而**求和后仅 0.09**（单槽却是 1.8–3.9 ⇒ 各槽互相抵消）⇒ `λ·0.09` 对 `CE≈15` 完全被淹没。**2026-09-29 已修**（改为逐槽 + 全位置 KL），修复后 `all-active` 从 1/4 升到 **2/4**、生成退化（复读）消失 |

#### T1 补充 · 模型规模决策（2026-09-29 用户确认）

- **用户决定**：**用尽可能小的模型**，只要能把"思路正确且有效"证明出来即可（设备较弱）。
- ⇒ **主基座改为 Qwen3-0.6B**；1.7B 降为**规模对照**（用来检查结论是否随规模变化，而不是主实验平台）。
- 【实测】同一套探针在 0.6B 上的复现（4 条记忆、每条 15 步写入、同一个 episode 种子）：

  | 读取方式 | 1.7B | **0.6B** |
  | --- | --- | --- |
  | 只开本条自己的槽 | 4/4 | **4/4** |
  | 只开别的槽（P4 的 SHUFFLE） | 0/4 | **0/4** |
  | 开全部槽 | 1/4 | **2/4** |
  | 写入耗时/条 | 32–33 s | **15–17 s** |
  | 峰值显存 | 数 GB | **1180 MB** |
  | 侧路参数量 | 112 模块 / 19.27 M（12 槽） | 112 模块 / **9.18 M**（8 槽） |

- **结论**：① "写得进（单槽 4/4）、擦得净、读时叠加是瓶颈"这套结论**在两个规模上都成立**
  ⇒ 机制是否成立已经不被算力卡住；② 0.6B **快一倍、显存省一个数量级**
  ⇒ **T2–T6 全部在 0.6B 上做**，论文主表以 0.6B 为主、1.7B 作规模对照
  （"能否外推到更大模型"仍写进 limitation）。

### T2 · 读时组合：把"和"换成"选"　【下一步，等方向确认】

| 项 | 内容 |
| --- | --- |
| **做什么** | 解决"各槽输出直接相加互相覆盖"。三条候选：**(a) 读时稀疏路由**（用查询与各槽键的相似度选 top-1/top-2）；**(b) 写时正交化**（约束各槽贡献互不撞车，保留全量相加）；**(c) 归一化各槽贡献的幅度** |
| **产物** | `src/parammem/memory/router.py`（或写入侧正交约束）+ `experiments/t2_composition.py`：`全量相加 / top-1 / top-2 / oracle` 的消融表 |
| **退出判据** | `all-active EM` 接近 `own-only EM`（当前 1/4 vs 4/4）；**同时报告路由错时的错答率**（因为路由错会自信地答错） |
| **为什么必须在这一步** | 【实测】1/4 与 4/4 之间就是全部可改进空间，且它现在**完全挡住了后面所有阶段**——T4 的容量实验、T5 的惯性实验都要求"多条记忆共存时可读" |
| **⚠️ 代价** | 引入路由会削弱"读取不需要检索步骤"这个卖点。README 里那句话**必须同步改**，不能装作没变 |

**【实测】已知的边界条件（写进判据用）**：错答是"看着像真的"的混合体（`#40D96C60 60D66C`、`April 25, 1444 – April 25,`）；
干扰**不是"新压旧"**（最后写入的那条同样失败）。

**【实测】叠加是"阈值型"而不是渐变**（0.6B，累积写入 1 → 2 → 4 → 8 条，`_dev\probe_scaling.py`）：

| 已写条数 | 1 | 2 | 4 | 8 |
| --- | --- | --- | --- | --- |
| `own-only`（只开本条自己的槽） | 1/1 | 2/2 | 4/4 | 8/8 |
| `all-active`（全开） | 1/1 | 2/2 | **0/4** | **0/8** |

⇒ **能共存 2 条，到 4 条直接归零**。这给 T2 定了一个明确的目标：把"全开"从 0/8 拉回接近 8/8，
而不是追求"略微改善"。锚定项修好之后，4 槽的 `all-active` 已从 1/4 升到 **2/4**（见 T1 补充）。

### T3 · 写入判据：什么该刻成钢印

| 项 | 内容 |
| --- | --- |
| **做什么** | 实现三种判据并与"全写"对照：**(a) 惊讶度**（写入前该内容的负对数似然超阈值才写）；**(b) 显式指令**（用户说"记住"）；**(c) 信息增益**（写前/写后对探针的似然差） |
| **产物** | `src/parammem/memory/criteria.py` + `experiments/t3_write_policy.py` |
| **退出判据** | 在**同等上下文预算**下，判据策略的"净收益/写入成本"优于全写；报告**误写率**（写进去但从没被召回过的比例）与**漏写率**（该记却没写的比例） |
| **为什么重要** | 真实对话里"什么值得记"**没有标签**。这是本项目三个最有研究价值的问题之一（另两个是遗忘、归因） |

### T4 · 遗忘与容量：只忘该忘的

| 项 | 内容 |
| --- | --- |
| **做什么** | ① 容量上限 K + 淘汰策略对照（**FIFO / LRU / LFU / 效用 / 效用+时间衰减**，代码已就位）；② 效用衰减与时间衰减；③ 重要性硬保护（"钢印"不参与淘汰）；④ 测**基座能力漂移** |
| **产物** | `src/parammem/memory/store.py`（已完成）+ `experiments/t4_capacity.py` |
| **退出判据** | 画出**容量 – 保留率 – 基座漂移**三维曲线；`保留率@重要 − 保留率@噪声 > 0`（即"只忘该忘的"） |
| **必须一起测的东西** | 【文献】连续编辑会让被改矩阵的**范数持续增长**（arXiv:2502.01636）⇒ 每轮都要记录槽范数（代码已记录） |
| **⚠️ 前置隐患（2026-09-29 已修）** | 锚定项过去是空转的（按求和求 KL ⇒ 各槽抵消后仅 0.09，被 CE≈15 淹没）。已改为**逐槽 + 全位置** KL（`--anchor-mode slot` 为默认，`sum` 保留作消融）。T4 的"基座漂移"指标仍需换成更合理的判据（现用答案字符串全等，过严） |

**【文献】为什么这条路值得做**：防遗忘的论文极多，**主动可控遗忘极薄**——只有 FADE 一篇把遗忘当一等公民，
且只作用于最后一层、无现成代码；淘汰策略唯一有硬数字的研究显示"没有策略比 LFU 好超过 0.041 个百分点"。
⇒ **淘汰策略的收益极易被高估**，所以我们必须把所有策略放在同一批轨迹上比，而不是只报自己那套。

### T5 · 上下文惯性：记忆不该占据"当前现实"

| 项 | 内容 |
| --- | --- |
| **做什么** | ① 先建**惯性基准**（【文献】确认**不存在**专门基准，需自建：Lost-in-the-Middle 的位置置换 + GSM-IC 式无关上下文干扰 + sycophancy 三块拼图）；② 三臂对照 **`无记忆` / `上下文记忆` / `参数记忆`** |
| **指标** | **I1 主题残留**（切换话题后回答与旧话题的相似度）、**I2 前提继承**（旧话题的**错误前提**是否被带进新话题）、**I3 反复纠结**（复述上文的句子占比）+ 任务成功率（防止"为了不纠结而不干活"） |
| **产物** | `bench/inertia.py`（`synthetic.py` 里已有惯性块雏形）+ `experiments/t5_inertia.py` |
| **退出判据** | 参数记忆臂的 I1–I3 显著低于上下文记忆臂，且任务成功率不下降 |
| **⚠️ 必须做的公平性处理** | 两臂的**信息量必须对齐**（上下文臂不能故意塞爆上下文），否则会被质疑"对手本来就吃亏" |

### 我修正了你框架里的三处（必须说清，否则后面会踩）

1. **"扩展一个矩阵/层"的直觉，方向对但重心要挪。**
   实测表明**容量不是瓶颈**——19.27 M 参数足够让 4/4 条记忆各自被完美召回；
   **真正的瓶颈是读的时候多条记忆怎么共存**（全开 1/4）。
   ⇒ 所以 T2 被插到路线里，工作量从"把记忆模块做大"转向"**读时怎么取**"。
2. **"像人脑一样遗忘"做成了更强的形式。**
   人脑遗忘是启发式衰减，无法断言"这条真的没了"。我们做成**精确擦除**：
   擦除后输出与"从未写过"**逐字符相同**【实测 5/5】。代价是容量变成离散的 K。
3. **主张必须限定范围。**
   【文献】长上下文在 QA 上**普遍优于** RAG（arXiv:2501.01880），且 20–25% 的失败是"上下文已充分但模型不会用"
   （arXiv:2411.06037）。⇒ **不得**声称"参数记忆普遍优于上下文"，只能限定在三个条件：
   **① 跨会话持久；② 需要遗忘；③ 需要抑制上下文惯性。** 这三条之外的场景，长上下文是更强的方案。
